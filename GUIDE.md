# Инструкция v0.3.4

## Проход мастера от запуска до проверки

### 1. Подготовьте две VDS и откройте терминал

Вход принимает подключения телефона по HTTPS. Через выход трафик попадает в интернет. Выпишите из панелей провайдера публичный IPv4 и способ первоначального root-доступа для каждой роли. Для переноса подготовьте отдельное тестовое имя с A-записью на новый вход. Рабочий домен переключайте отдельно после испытаний. Поддерживаемые образы — Ubuntu 24.04 и 26.04, amd64.

Скопируйте одну команду для своей ОС из [README](README.md). На Windows откройте обычный PowerShell, на macOS — Terminal. Вручную заходить на VPS перед запуском не требуется. Вопросы остаются в этом окне. Обе VDS скачивают комплект самостоятельно. Для установки OpenSSH или запуска системного ssh-agent Windows при необходимости покажет запрос повышения прав.

### 2. Укажите серверы и разблокируйте ключ

В Q03 укажите вход, в Q05 — выход. На чистой установке достаточно двух адресов вида `root@IP`. При переносе укажите новый вход и действующий выход. Если для выхода уже есть рабочее SSH-имя, можно ввести его.

В Q09 укажите путь к **приватному** файлу, например `id_ed25519`, или введите `new` для создания пары. Файл с окончанием `.pub` нужен для добавления доступа на сервер. При запросе `Enter passphrase` введите фразу самого ключа. Символы при вводе скрыты. `Identity added` означает, что ключ разблокирован на компьютере. Если сервер ещё не знает ключ, в Q17 выберите пароль сервера или консоль провайдера и следуйте подсказке. Мастер затем проверит новое подключение по ключу. При первом подключении сверьте отпечаток с консолью провайдера.

### 3. Выберите маршрут SSH, только если потребуется

Когда прямое подключение удалось, Q18 пропускается. Если Q18 появился, смотрите, **какой адрес указан в заголовке и какой промежуточный сервер указан в строке выбора**.

- **1** использует переход из SSH-настроек компьютера. Например, при переносе через прежний вход мастер покажет его SSH-имя. На компьютере без настроенного перехода такого варианта нет.
- **2** проверяет путь через вторую VDS установки. Для новой пары этот путь возможен, если доступен первый сервер, он разрешает SSH-переадресацию и второй принимает SSH с его адреса. Чистый образ сам по себе этого не гарантирует.
- **0** останавливает мастер. При сетевой ошибке выбранного маршрута можно выбрать другой в Q18. Сообщение о недоступности само по себе не указывает, какой firewall или участок сети помешал. Ошибку авторизации разбирайте в Q17, несовпадение отпечатка — через консоль провайдера.

Маршрут Q18 служит компьютеру для управления установкой. Для переноса входа выбирайте рабочий маршрут к выходу, даже если он проходит через старый вход. Перед отключением старого входа проверьте новый независимый путь к выходу. В Q23 при желании сохраните имя проверенного подключения. Команда `ssh nnh1` заработает, если именно такой алиас создан в SSH-настройках компьютера.

### 4. Выберите действие и режим

В Q13 можно передать локальный **экспорт учётных данных** для сохранения прежних логинов и паролей. Профиль телефона используется позже. Для новой пары оставьте Q13 пустым. При переносе исходной установки, если нужно сохранить доступ старых клиентов, подготовьте экспорт до применения. [Формат экспорта](CLIENT_EXPORT_V1.md)

| Задача | Q00 — действие | Q01 — какие серверы настраивать |
|---|---|---|
| Посмотреть план и закончить | 1 — preview | Выберите интересующий режим |
| Настроить две новые VDS | 2 — new | 1 — fresh |
| Испытать новый вход с действующим выходом | 2 — new | 2 — replace-entry |
| Подключить новый выход к действующему входу | 2 — new | 3 — replace-exit |

Q02 — имя установки, по которому мастер находит файлы, службы и сохранённые параметры. Для первого переноса исходной схемы выберите новый ID, например `nnh1`. Для продолжения той же установки введите прежний. Допустимы 3–10 строчных латинских букв и цифр, первая — буква. Повтор Q02 с сообщением об ошибке означает, что значение нужно исправить. ID и SSH-алиас задаются независимо.

### 5. Сверьте параметры VPN

В Q04 и Q06 укажите публичные адреса входа и выхода соответственно. Q07 — домен для сайта и сертификата. В Q08 для сохранённой ноды исходной схемы проекта выберите **1 — legacy**. Для ноды, которую этот мастер уже настраивал под тем же ID, выберите **2 — managed**. Для двух новых нод Q08 пропускается.

Q10–Q12 мастер подбирает сам. Это внутренняя сеть WireGuard между VDS, служебная сеть внутри входа и UDP-порт WireGuard на выходе. Порт из плана понадобится, если доступ ограничивает firewall в панели провайдера. Q15 позволяет дополнительно защитить IP резерва и старого входа. Если в `blocked_ips` видны адреса нового входа и выхода, это запрет для **запросов VPN-клиента к этим адресам**. SSH мастера и соединение WireGuard продолжают использовать эти адреса.

В Q16 выбирайте **1 — ready**, если тестовый домен уже ведёт на вход и порты TCP 80/443 доступны для выдачи сертификата. Выбор **2 — defer** откладывает проверку HTTPS и клиентского подключения. После готовности DNS запустите `verify`. В Q20 выберите **2**, чтобы исправить конкретный ответ, или **1**, чтобы увидеть план. Переход от Q20 к плану ещё не применяет его.

### 6. Прочитайте план и подтвердите установку

В плане пути под `entry` относятся к файловой системе входной VDS, под `exit` — выходной. Сверьте адреса, домен, роль сохраняемой ноды и строки `update`. Открывать вручную каждый будущий файл не требуется. При замене входа с исходным выходом ожидайте следующие изменения:

- Новый вход получает Caddy, sing-box, изолированную сеть, сайт и службы. Ему создаётся новый ключ WireGuard.
- Действующий выход получает дополнительный туннель и правила для него. Его собственный ключ и прежний туннель сохраняются. Строка `update /etc/nftables.conf` означает реальное изменение firewall действующего выхода.
- Старый вход может участвовать как промежуточный SSH-сервер. Переключение рабочего DNS и удаление старого входа выполняются отдельно.

Если план соответствует согласованным работам на **обеих** VDS, в Q19 введите латиницей `APPLY`. Enter или `stop` завершат мастер до применения. В режиме preview мастер завершится после показа плана.

### 7. Следите за этапом и результатом

`entry / prepare` означает подготовку пакетов на входе. Сборка Caddy при необходимости занимает несколько минут. На выходе prepare проверяет сетевые пакеты и ключ WireGuard. Счётчик каждые 20 секунд показывает, сколько мастер ждёт операцию; это не процент выполнения. Предел этапа prepare — 40 минут на роль. Проверка SSH с надписью «up to 25 seconds» имеет отдельный лимит.

Затем мастер применяет сетевые изменения сначала на выходе, потом на входе и открывает новые SSH-сессии для фиксации. Строка `exit: applied` означает завершение шага на одной роли. Если следом появились `exit: rolled-back` и `Command failed: systemctl`, установка завершилась ошибкой. Запишите роль, последнее действие и имя службы, если показано. Через действующий SSH или консоль проверьте `systemctl --failed` на этой VDS. После обрыва сверьте состояние обеих ролей и таймеры; при подтверждённом откате и устранённой причине повторите запуск с Q00 → **3 — apply-saved** и прежним ID. [Восстановление после прерывания](#повтор-прерывание-откат)

### 8. Сохраните профиль и передайте сайт

После успешной фиксации мастер покажет логин `master_user` и пароль в терминале. Сохраните их приватно. В Q24 укажите путь к **новому файлу** на компьютере, перенесите JSON на Android и импортируйте в SFA как локальный профиль. Разрешите Android создать VPN-подключение. Экспорт из Q13 предназначен для мастера, а файл из Q24 — для телефона. [Клиент, настройки профиля и адрес будущей панели](#выдача-профиля-и-публикация-сайта)

1. Для собственного сайта заранее [скачайте ZIP-заготовку](https://raw.githubusercontent.com/alxkirshenbaum-hue/empire451f/v0.3.4/dist/site-handoff-example.zip). Приложите её к сообщению агенту, например: «Сделай сайт об истории маяков по инструкциям внутри. Сохрани структуру и верни готовый ZIP». Доступ к VDS и профиль VPN агенту не нужны.
2. В Q25 укажите путь к **возвращённому агентом ZIP** на компьютере. Мастер проверит архив и опубликует каталог `site/`. Инструкции агенту остаются за пределами публичного сайта. Если сайт пока не готов, нажмите Enter, чтобы оставить текущий вариант. После публикации откройте домен Q07 по HTTPS и проверьте страницу.

### 9. Проверьте результат перед переключением рабочего домена

Запустите ту же команду, выберите Q00 → **4 — verify** и прежний ID. Проверьте сайт, TCP, UDP через UoT и совпадение внешнего IP с Q06. Откройте отдельную SSH-сессию к каждому серверу. Включите профиль на телефоне и проверьте доступ через VPN к ресурсу, который профиль направляет в туннель. Сценарии Q00 → **6** и **7** включают отключение WireGuard и перезагрузки соответственно; для работающего выхода выделите отдельное окно. Для переноса с тестового домена пользуйтесь [планом переключения и возврата DNS](MIGRATION_TEST.md).


## Как сменить тестовый домен на рабочий

**Если меняется только IP**, а клиент уже использует домен и новая VDS обслуживает тот же домен, достаточно обновить A-запись и переподключить клиент после истечения DNS-кэша. На новой VDS должны работать HTTPS и прежние учётные данные. **Если меняется само имя**, его должны знать Caddy и клиент: сертификат на тестовое имя не подтверждает рабочее имя. DNS определяет адрес, а Caddy на входе получает сертификат для имени из Q07.

1. Сначала проверьте тестовую установку. Q00 → **4** проверяет сайт, TCP, UoT и внешний IP выхода. Убедитесь также, что у вас сохраняется SSH-доступ к выходу после отключения старого входа.
2. Снова запустите мастер и выберите Q00 → **3 — Apply saved settings (change domain or other settings of existing VPN, retry a previous installation)**. Мастер загружает сохранённые настройки существующих нод, открывает их для редактирования и показывает план до применения. Q00 → 1 заканчивается просмотром плана. Q00 → 2 предназначен для настройки новых серверов. Укажите в Q02 **прежний ID** этой установки, например `nnh1`. В Q13 достаточно нажать Enter, если действующие учётные данные уже сохранены на входе.
3. Оставьте прежние серверы и режим. В Q07 замените `empire451f-t.duckdns.org` на `empire451f.duckdns.org`. В Q16 ответьте по факту: **2**, пока рабочая A-запись ведёт на старый вход; **1**, если DNS уже обновился и новый вход доступен по TCP 80/443. При выборе 2 окончательная проверка HTTPS откладывается. До перехода на DNS рабочего имени возможен перерыв доступа через тестовое имя.
4. На Q20 откройте план. Сверьте домен, адреса и изменения Caddyfile на входе. Для одной смены имени новые ключи, туннель и порт на выходе не требуются. Неожиданные изменения сети разберите до подтверждения Q19. После `APPLY` дождитесь фиксации и в Q24 сохраните новый профиль под новым именем файла. При Q25 нажмите Enter, чтобы оставить прежний сайт.
5. Направьте A-запись рабочего домена на новый вход. Для IPv4-установки убедитесь, что у рабочего имени нет устаревшей AAAA. В PowerShell команда `Resolve-DnsName empire451f.duckdns.org -Type A` покажет адрес, который сейчас видит ваш компьютер. Дождитесь действительного сертификата на рабочее имя и запустите Q00 → **4** с тем же ID. На телефоне импортируйте новый профиль, подключитесь и проверьте внешний IP трафика, идущего через VPN.
6. До приёмки сохраните старый вход и старый профиль. Для возврата направьте A-запись на прежний вход. Клиенты с доменом подхватят адрес после обновления DNS-кэша и переподключения. Для профиля с закреплённым IP выберите копию для старой VDS. Установщик DNS не переключает.

**Как устроен новый профиль.** Начиная с v0.3.1 в Naive-подключении указан один адрес — домен в поле `server`. SFA использует его также для проверки сертификата. Чтобы найти вход до подключения VPN, профиль разрешает его имя через отдельный прямой DNS-over-HTTPS к Cloudflare по IPv4. Число `1.1.1.1` в секции DNS — адрес резолвера, а не VDS. Этот запрос раскрывает имя входа резолверу; доступность прямого DoH нужна для запуска. Для обычных DNS-запросов профиль использует DoH через туннель. [Реализация Naive в sing-box 1.14.4](https://github.com/SagerNet/sing-box/blob/v1.14.4/protocol/naive/outbound.go)

**Ранее выданные профили.** В v0.3.0 поле `server` содержало IP. Смена A-записи такую копию не обновляет. Для `master_user` импортируйте новый файл Q24. Для другого логина сделайте приватную копию нового шаблона профиля с учётными данными именно этого клиента. Сохраните прежний файл до проверки. При следующих заменах IP с тем же доменом повторная выдача доменного профиля не требуется.


## Что запускается

Windows запускает штатный PowerShell/OpenSSH, macOS — штатный bash/OpenSSH. Локальный Python, Git-клиент, клонирование, распаковка и локальные шаблоны не нужны. Короткий запускающий текст выполняется в памяти терминала. Временный SSH-config (а на macOS также FIFO и сообщения ошибок транспорта) генерируется локально и удаляется при завершении; это не скачанный комплект программы. Новые SSH-ключи и known_hosts остаются на компьютере по явному выбору пользователя.

Полный комплект v0.3.4 скачивают **сами обе VPS** из Git, сверяют закреплённый SHA256 и исполняют в памяти. Общий диалог и координация — `controller.py` на входной VPS; конфигурации — `render.py`; применение и откат обеих ролей — один `remote.py`. `client.py` сохраняет общие тексты вопросов и инструменты локальных тестов разработчика; его прежний локальный orchestration-путь в пользовательском запуске не используется.

Диалог идёт в исходном терминале через `ssh -tt`. Чтобы не передавать SSH-ключи или ssh-agent на сервер, запускающий код держит два SSH-соединения и соединяет серверные части через локальный и обратный TCP-туннели. RPC выхода слушает только127.0.0.1, требует случайный сеансовый токен, прекращает работу при штатном закрытии или через2часа. Токен и необязательный импорт передаются зашифрованными SSH environment requests (`LC_EVPN_*`), без аргументов командной строки и файлов с токеном. Клиентские пароли не передаются выходной VDS.

Поддерживаемая ОС серверов — Ubuntu 24.04/26.04 amd64/systemd, root. Нужны обычные для чистой Ubuntu настройки OpenSSH: `AcceptEnv LANG LC_*` и разрешённое TCP forwarding. Проверка LC_* выполняется экспериментально до загрузки кода; туннели создаются с ExitOnForwardFailure. Эти настройки установщик автоматически не ослабляет. Если образ был специально ограничен, проверьте `sshd -T` через консоль провайдера; изменение SSH требует отдельного решения. Облачный firewall должен пропускать SSH, затем TCP80/443 входа и UDP-порт Q12 выхода от IP входа. Панель провайдера установщик не изменяет.

**B01** — при отсутствии Windows OpenSSH Client предлагается установить системный компонент Microsoft, с UAC. На macOS используются предустановленные ssh/curl/openssl/base64. Python нужен только на VPS; если его нет в минимальном образе, Q22 отдельно предлагает установку после проверки платформы. Внешний первый запуск доверяет HTTPS GitHub; SHA256 серверного комплекта встроен в закреплённый загрузчик.

## Вопросы мастера

Серверные ответы можно исправить на Q20: введите обозначение вопроса. Локальные SSH-параметры задаются до соединения; для их изменения перезапустите ту же команду. Невалидная конфигурация не допускается к SSH/установке. Пути допускают пробелы и Unicode, `~` означает домашнюю папку; укажите путь без внешних кавычек.

| ID | Назначение, источник сведений, ответы и последствия |
|---|---|
| Q00 | Выберите действие для этого запуска. Enter или 1 (`preview`) показывает план. 2 (`new`) — заполнить параметры и перейти к подтверждению APPLY; 3 — изменить домен или другие сохранённые параметры либо повторить установку; 4 — проверить работающий VPN; 5 — откатить последнюю транзакцию; 6 — приёмка с отказом WG; 7 — проверка с перезагрузками; 8 — защита SSH существующей установки. Название действия тоже принимается. Режим замены входа или выхода выбирают отдельно в Q01. |
| Q01 | 1 — новая пара, 2 — заменить только вход, 3 — заменить только выход. Режим. `fresh`: две чистые VDS. `replace-entry`: новый вход и сохранённый выход, рекомендуется для первой приёмки. `replace-exit`: сохранённый вход и новый выход. Старую ноду установщик не удаляет. |
| Q02 | При неверной длине мастер показывает количество введённых символов. После принятия ID в preview повторный ввод не требуется.  Постоянный ID, 3–10 строчных латинских букв/цифр, первая буква. Выберите, например, `personal`. При повторе тот же ID: так находятся прежние ключи и журнал. Для параллельного legacy-переноса используйте новый ID. |
| Q03 | `root@IP` нового/сохранённого входа или SSH alias из `~/.ssh/config`. Источник — панель VDS. Alias раскрывается локально; параметры старого ProxyJump не принимаются за доказательство прямой доступности. |
| Q04 | Публичный IPv4 входа из панели. Не hostname. Именно эта VDS будет принимать HTTPS. |

## Первое подключение

1. Создайте VDS Ubuntu 24.04/26.04 amd64; откройте web/VNC-консоль и получите root-пароль либо заранее добавьте публичный ключ через панель.
2. Сравните показанный SSH fingerprint с `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` в консоли. Мастер никогда не отключает проверку host key. Изменённый ключ автоматически не заменяется: проверьте причину через провайдера.
3. Если root-парольный SSH запрещён, выберите Q17=`console`. Команда добавляет публичный ключ, не копирует приватный. На серверах с sudo-only доступом получите root-доступ через консоль; неявная настройка sudo не выполняется.
4. При собственной VPN на компьютере убедитесь, что административный маршрут достигает VDS: доступ к IP самого входа через его прокси намеренно запрещён.

## Повтор, прерывание, откат

На компьютере не сохраняются комплект программы, deployment.json или созданные клиентские пароли. На **входной VPS**: `/var/lib/empire-vpn/ID/deployment.json` и `clients.json` в каталоге0700, файлы0600. Последний файл — готовый экспорт для будущего переноса. При необходимости пользователь забирает его отдельно по SCP в защищённую папку вне Git. Не выводите содержимое в терминал/отчёт. Серверные WG-ключи генерируются на соответствующих VDS и не скачиваются.

На VDS: `/var/lib/empire-vpn/ID`0700 содержит ключ, метаданные транзакции и отдельный root-only каталог `transactions/TX/backups` с точечными резервными копиями0600. Содержимое конфигураций с секретами не включается в журнал: в нём только ссылки на копии. Файлы `/etc/empire-vpn/ID`, dedicated nft table и systemd units принадлежат конкретному ID. Изменённые извне или неизвестные файлы автоматически не перезаписываются. При неизменном повторе службы не перезапускаются. Установка зависимостей и сборка идут до сетевой транзакции; установленные пакеты, сборочный кэш, служебный пользователь и WG-ключ при откате остаются, чтобы повтор не менял секреты.

Перед изменением сети сохраняются точечные копии и ставится постоянный systemd timer на30мин. `Ctrl+C`, потеря компьютера/SSH или ошибка применения оставляют таймер; обычная ошибка вызывает немедленный откат. Сервер возвращает код42 после применения; запускающий код открывает НОВЫЕ ключевые SSH-сессии к обеим нодам и лишь затем вызывает серверную финализацию. Фиксация разрешена после этих сессий и обязательных проверок. Нет распределённой атомарности между двумя VDS: при обрыве терминала/координатора одна уже может быть зафиксирована, а другая откачена таймером. У обеих сохранён последний журнал; восстановите доступ и выполните `rollback` обеих либо продолжайте только после сверки состояния.

`rollback` отменяет последнюю транзакцию обеих ролей, восстанавливает только перечисленные файлы/службы и собственную nft table, не загружает полный старый host ruleset. В консоли конкретной VDS можно выполнить `python3 /var/lib/empire-vpn/ID/transactions/TX/remote.py rollback-local /var/lib/empire-vpn/ID/transactions/TX`. Старый журнал не может отменить более новую транзакцию. При чужом изменении файлов откат останавливается и требует ручной сверки, вместо уничтожения чужих изменений.

Legacy-выход: добавляется отдельный WG-интерфейс, прежняя пара ключей используется повторно; старый туннель остаётся. В `personal_host` добавляются маркированные разрешения, а его постоянный `/etc/nftables.conf` точечно дополняется; глобальная перезагрузка nft ruleset не выполняется. Legacy-вход при замене выхода: сохраняются собственный WG-ключ, службы, credentials и реле; обновляются peer/endpoint и известные ACL. При managed-замене с тем же ID WG-соединение переключается и возможен краткий перерыв.

## Проверки после установки

- `preview`: чтение SSH/платформы/маршрутов и перечень файлов, без постоянной записи. Для первого принятия host key нужен обычный мастер, preview его не добавляет. Локальный offline-preview в `client.py` предназначен только для разработческих тестов; пользовательский preview выполняется на VPS. Временные SSH-туннели/RPC — транспорт сеанса, постоянные настройки они не меняют.
- `verify`: временный клиент sing-box на входе, доверенный TLS, сайт, TCP HTTPS и UoT v2 DNS/STUN через Naive. Целевой служебный порт UoT — **0**. Проверяются запрет private UDP/IPv6 и новые SSH.
- `acceptance`: сначала verify; после отдельного `FAIL-CLOSED` WG входа отключается, проверяется отказ TCP/DNS/IPv6, затем восстановление. Есть отдельный 120-секундный таймер подъёма WG. Это выборочные активные проверки, не полный packet capture.
- `reboot-test`: отдельное `REBOOT`, по очереди выход/вход; новые bootID, отсутствие ordering-cycle в журнале, повтор verify. Применяйте только в согласованном окне работ.

Для любого повторного действия снова выполните ту же команду README: Q03/Q05/Q09 подключают узлы, затем Q00 выбирает действие и Q02 — сохранённый ID. Ручное редактирование JSON не требуется.

Первое реальное получение и будущее продление ACME требуют доступности DNS и TCP80/443. Старое TLS-хранилище не требуется. Встроенный минимальный сайт устанавливается автоматически; перенос прежнего сайта и панель пользователей в v1 не входят.

## Закреплённые источники

`versions.json`: Go1.27.3, Caddy2.11.9, xcaddy0.4.7, конкретный commit forwardproxy, sing-box1.14.4. Go и sing-box проверяются по закреплённому SHA256. Caddy собирается из официальных Go-модулей с GOSUMDB; транзитивные зависимости определяются их go.mod. Пакеты Ubuntu берутся из подписанных репозиториев ОС: их версии не заморожены, пакетная установка не откатывается. Новая версия компонентов требует отдельного выпуска установщика.

Официальные источники: [Go](https://go.dev/dl/), [Caddy](https://github.com/caddyserver/caddy), [xcaddy](https://github.com/caddyserver/xcaddy), [Naive forwardproxy](https://github.com/klzgrad/forwardproxy), [sing-box1.14.4](https://github.com/SagerNet/sing-box/releases/tag/v1.14.4), [HTTP inbound](https://sing-box.sagernet.org/configuration/inbound/http/), [Python](https://www.python.org/downloads/release/python-31210/).

При отказе разблокировки Q09 сохраняет путь: Enter повторяет попытку, другой путь меняет ключ, stop завершает запуск. Ошибка файла импорта возвращает к Q13. При долгой серверной операции мастер показывает роль, действие и прошедшее время каждые 20 секунд. После обрыва во время применения проверьте состояние транзакции и таймеры отката перед повтором.

На новой ноде рабочий файл существующего ключа создаётся с правами 0600 в /etc/wireguard/evpn-ID.key для штатного профиля AppArmor. Исходный ключ установки сохраняется. Для исходной ноды legacy путь к ключу остаётся прежним. После отката с сохранёнными параметрами используйте Q00 → 3 (apply-saved) и прежний ID.

**Q24.** Укажите путь к новому файлу, например `C:\Users\your-name\master_user.sfa.json`, либо нажмите Enter. Частные IP, домены .ru/.su/.рф, geosite-ru и geoip-ru идут напрямую; списки Hiddify загружаются через VPN каждые 120 часов. Для системного Android Download Manager прямой маршрут имеет исключения для доменов OpenAI из образца. Остальной трафик идёт через VPN. При отложенной проверке TLS сначала подготовьте DNS и сертификат.

**Q25.** Локальный путь к ZIP (до 200 МиБ) или Enter, чтобы оставить сайт как есть. [Скачайте заготовку](https://raw.githubusercontent.com/alxkirshenbaum-hue/empire451f/v0.3.4/dist/site-handoff-example.zip), передайте архив агенту с темой и заберите готовый ZIP в той же структуре. ## Защита SSH после установки

После успешной установки и проверки новых ключевых соединений мастер предлагает дополнительные ограничения. Для уже установленной пары откройте Q00 → **8** (`ssh-security`) и прежний ID. Одинаково подходит одна проверенная локальная пара ключей или отдельные ключи. Проверка должна пройти для каждой ноды по реально выбранному маршруту.

- **Q26**. Есть ли доступ к аварийной web/VNC-консоли обеих VDS? Выберите `y`, только если сможете войти туда независимо от SSH. Enter завершает этот шаг без изменений.
- **Q27**. Включить вход строго по публичному ключу для всех пользователей обеих нод? При `y` мастер добавляет отдельный файл OpenSSH, проверяет синтаксис и эффективную политику, затем перечитывает SSH. Существующие ключи сохраняются.
- **Q28**. Разрешить новые SSH-подключения к выходу только с IPv4 входа? Предлагается, когда выход действительно видит этот адрес источником административной сессии. При `y` меняются постоянные и действующие правила на выходе. Штатный путь к выходу далее требует доступного входа; запасной независимый доступ — консоль провайдера. На входе доступ к SSH по IP источника этот шаг не ограничивает.

Enter в Q27 или Q28 пропускает соответствующую настройку. Изменения защищены таймером точечного отката на каждой затронутой ноде. Для их фиксации мастер повторяет ключевой вход на обе VDS, в том числе через выбранный ProxyJump. При разрыве связи проверьте состояние обеих сторон: фиксация на разных VDS выполняется последовательно. Для legacy-нод эта опция пропускается. Правила облачного firewall управляются через панель провайдера.

## Аудит безопасности после установки

На Windows откройте обычный PowerShell под той же учётной записью, что и для установки. Подготовьте SSH-алиасы обеих нод, проверенные ключи сервера в known_hosts, разблокированный ключ и ID установки. Команду можно повторять после изменений. Она предназначена для пары, развернутой этим установщиком на чистых VDS.

```powershell
& ([scriptblock]::Create((Invoke-WebRequest -UseBasicParsing 'https://raw.githubusercontent.com/alxkirshenbaum-hue/empire451f/v0.3.4/Audit-Vpn.ps1').Content))
```

Для текущей пары ответы по порядку — `hh-entry`, `hh-exit`, `nh1`. Аудитор открывает новые SSH-сессии, учитывает ProxyJump из SSH-конфигурации и выводит результаты по ролям. При недоступной ноде, ошибке измерения или отклонении от критерия запуск завершается ошибкой. Строка FAIL указывает, какую проверку нужно разобрать. Повторный запуск ничего не исправляет автоматически.

Проверяются фактические UID, capabilities и namespace обоих процессов, маршруты SSH и WG, DNS, права ключей, слушатель HTTP CONNECT, хэши файлов, активные правила nftables, состояние служб и граф systemd. Для сравнения nftables эталон загружается в отдельный временный сетевой namespace. Проверка с выхода включает TLS 1.2/1.3, h2, SNI, сайт, 404 и ответы на CONNECT без действительных учётных данных. На входе временный клиент проверяет TCP и UDP/STUN с ожидаемым IP выхода, DNS через UoT и запрет проб к private UDP и IPv6. Пароли и приватные ключи в результат не входят.

Исторический критерий SSH включает прямой запрет парольного root-входа через PermitRootLogin и фильтр на выходе по IP входа. Аудитор показывает запрет PasswordAuthentication и KbdInteractiveAuthentication отдельно. Правило в таблице установщика, политика провайдерского firewall и доступность порта со всего интернета — разные измерения. Сверка правил с манифестом обнаруживает расхождения с зафиксированной установкой, но не заменяет независимый анализ всех правил хоста.

**Расширенный аудит с отключениями.** Добавьте `-Disruptive` в конец команды после закрывающей скобки. Откройте обе аварийные консоли у провайдера. После обычных проверок мастер потребует ввести `OUTAGE-AND-REBOOT`. При испытании отключается WG, проверяются уже открытое TLS-соединение и новые TCP/DNS/IPv6, затем восстановление VPN. Далее по одному завершаются процессы Caddy и sing-box, пересоздаётся namespace. Поочерёдно перезагружаются выход и вход. После каждого reboot проверяются смена boot ID, свежий SSH на обе ноды и TCP/UoT/сайт. Тест относится к программной перезагрузке ОС. Независимый захват всех пакетов и выключение питания через панель в него не входят. Итоговая ошибка статического аудита сохраняется даже при успешных отказных тестах.

**Отдельные испытания.** Q00 → 6 проверяет отказ трафика при отключении WG, Q00 → 7 перезагружает обе ноды. Выбирайте их в согласованное окно с открытыми консолями провайдера. Реальное восстановление после падения каждого процесса и после пересоздания namespace, наблюдение за физическим интерфейсом во время отказа и загрузки требуют отдельного контролируемого прогона. Настройка Restart и отсутствие сообщений о циклах в текущей загрузке не доказывают эти сценарии. Длина padding авторизованного CONNECT, полный захват Android, устойчивость к DPI, реальные продления ACME и нагрузка группы в автоматический результат не входят.
