# Первая практическая приёмка: новый вход HostHatch

План применения, **не выполнен**. Текущий вход KVMka193.233.22.225 и резерв193.233.22.78 не изменяются. Выход HostHatch85.155.184.194 сохраняется. Перед применением нужны отдельное согласование изменений выхода/новой VDS и её IPv4/root-доступ. Повтор старых deploy/switch/rollback скриптов не нужен.

1. Новая HostHatch: Ubuntu 24.04/26.04 amd64, рекомендуется >=1ГБ RAM и >=4ГБ свободного диска для сборки Caddy. Открыть консоли новой VDS и выхода. На Windows проверить административный маршрут, получить SSH fingerprint из консоли. Создать отдельный тестовый домен и после отдельного согласования направить его A на новую VDS; рабочий empire451f.duckdns.org пока оставить на KVMka.
2. Открыть публичный репозиторий и буквально выполнить Windows-команду README в PowerShell5.1/7. Проверить, что комплект v0.2.13 скачивают и сверяют по SHA256 сами VPS, а Windows использует только OpenSSH. Диалог должен оставаться в исходном терминале. Это первая проверка пользовательского сценария целиком; локальные unit tests её не заменяют.
3. Ответы: Q01=`replace-entry`; Q02=`hhentry`; Q03/Q04 — новая VDS; Q05=`hosth-exit`, Q06=`85.155.184.194`; Q07 — тестовый домен; Q08=`legacy`; Q09 — текущий административный ключ; Q10=`10.203.71.0/30`; Q11=`10.203.72.0/30`; Q12=`51830`; Q13 — экспорт прежних credentials либо скрытый ввод прежней пары; Q15=`193.233.22.78,193.233.22.225`; Q16=`ready` при готовом тестовом DNS, иначе `defer`.
4. Проверить прямой SSH обеих нод. Если выход по сети закрыт — в Q18 выбрать **1** (Enter), чтобы подключиться через `kvmka-entry` из SSH-настроек компьютера. Установщик использует старый вход только как SSH-транзит, его файлы/службы не меняет. Ошибку авторизации или host key исправить отдельно.
5. Просмотреть конкретный diff-перечень до APPLY: новая VDS получает компоненты, namespace и службы; на выходе новый интерфейс `evhhentry`, порт51830, прежний `/etc/wireguard/personal.key`, новые peer/subnet/NAT и маркированные разрешения в personal_host. Старый wg0/peer/маршрут остаются. Если инвентаризация не распознаёт текущую схему — остановиться; не обходить защиту force-перезаписью.
6. После отдельного разрешения ввести APPLY. Проверить новые SSH-сессии, namespace egress85.155.184.194. При ready дополнительно обязательны сайт, доверенный новый TLS и полный Naive TCP/UoT DNS/STUN. При defer результат только промежуточный: после готовности DNS запустить verify, до этого приёмку не объявлять.
7. В согласованном окне запустить acceptance и reboot-test. Для reboot-test здесь будут перезагружены **сохранённый выход и новый вход**; это требует отдельного допуска, поскольку выход обслуживает старых клиентов. При отсутствии допуска отложить reboot выхода и не отмечать полный сценарий PASS. Проверить namespace UID/capabilities, firewall, неизменный host default route, отсутствие ordering-cycle, новые SSH и ожидаемый egress. Зафиксировать фактические результаты, а не только активность systemd.
8. Только после успешной приёмки согласовать рабочее DNS-переключение. Повторить запуск, выбрать Q00=apply-saved с тем же ID/ключом/credentials, изменить Q07 на empire451f.duckdns.org и Q16=`defer`, просмотреть/согласовать изменение Caddyfile. Переключить A отдельно; дождаться публичного DNS, свежего ACME и verify. Старые профили с прежним доменом и credentials сохранят доступ после обновления DNS. Для временного домена нужен отдельный тестовый профиль, существующие профили не редактировать.
9. Обратное переключение: вернуть A рабочего домена на193.233.22.225. Старый вход, его сертификаты, credentials и WG остаются. При необходимости после согласования выполнить rollback последней сетевой транзакции нового ID на новом входе/выходе. DNS установщик не откатывает. При откате только последней смены домена более ранний параллельный туннель остаётся; его удаление отдельная операция.

Удаление старой KVMka, очистка старого туннеля, старых сертификатов и резервов в эту приёмку не входят.
