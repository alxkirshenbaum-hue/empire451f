## BL-007 · Читаемое имя скачанного профиля

## BL-008 · Доступ к панели только для owner и manager

**Статус:** Зафиксировано · **Дата:** 14.11.2026 · **Теги:** `ACCESS` `USERS` `DB` `API` `UI` `VPN` `PROFILES`

**Проблема:** адрес панели не должен быть доступен любому VPN-пользователю; с ростом числа пользователей доступ нужно ограничить явно выделенными людьми.

**Результат:** добавить пользователю атрибут роли с тремя значениями: `owner`, `manager`, `user`. У owner и manager панель открывается, у user — нет. На первом этапе не разрабатывать гибкий конструктор ролей и прав. Доступ к адресу панели и право выполнять операции в ней — связанные, но отдельные проверки; допустимые действия manager ещё нужно определить.

**Поле type:** владелец предложил переиспользовать его, если это не смешивает сущности. По текущей схеме `users.kind` содержит `regular`/`service`, участвует в защите master_user, ограничениях и неизменяемости идентичности. Это тип учётной записи, а не полномочия; предварительно предпочтительно отдельное поле `role`, сохранив `kind`. Соответствие отображаемого Type этому полю проверить при подготовке задачи.

**Уточнить и декомпозировать:**

- Определить границу запрета: требуется недоступность самого адреса/соединения, а не только отказ после входа. Найти способ надёжно связать VPN-подключение с пользователем и применить ограничение до выдачи страницы панели; общий IP выхода сам по себе не идентифицирует пользователя.
- Проверить, можно ли реализовать требование поверх текущей топологии без значительных изменений транспорта. Скрытие ссылки или исключение маршрута из выдаваемого профиля не считать достаточной защитой: пользователь может изменить профиль и обратиться напрямую.
- Согласовать назначение начальных ролей существующим пользователям и связь VPN-пользователя с административной сессией панели. Для новых пользователей предлагается роль user по умолчанию; служебный тип master_user автоматически не означает роль owner.
- Определить, кто назначает роли, полномочия manager внутри панели, защиту от повышения собственных прав и потери последнего owner. Зафиксировать простые правила без универсальной системы разрешений.
- Определить отзыв доступа при понижении роли: срок применения, уже открытые соединения и административные сессии. Учесть несколько нод из BL-003.

**Предварительная приёмка:** owner и manager открывают панель через VPN и проходят требуемую аутентификацию; user не получает доступ к панели, в том числе при прямом обращении по адресу/IP, через API и с вручную изменённым профилем. Проверены новые и существующие пользователи, смена роли, отзыв доступа и невозможность самоповышения. При недоступности источника ролей доступ не расширяется. Обычный VPN-трафик и административный SSH сохраняются. Способ ограничения и набор тестов уточнить до реализации; сетевые изменения требуют отдельного согласования.

## BL-009 · Баг: скачивание вложений ChatGPT в SFA 1.15 alpha13

**Статус:** Зафиксировано · **Тип:** Баг · **Дата:** 14.11.2026 · **Теги:** `VPN` `PROFILES` · **Связь:** W6, телефонная приёмка G6/G7

**Источник:** результаты пользовательского тестирования, сообщённые владельцем; агентом независимо не воспроизводились. Эти частичные результаты не закрывают телефонную приёмку.

### Контекст

Два реально работающих профиля SFA, по описанию владельца:

- **Daria — базовый Naive + UoT v2:** `route.final = naive-out`; без отдельных правил Android Download Manager и GeoSite/GeoIP RU; DNS Cloudflare DoH через VPN.
- **G3 Canary — расширенный W6:** тот же Naive + UoT v2; GeoSite/GeoIP RU и `.ru/.su/.рф` → `direct`; первое правило для `com.android.providers.downloads` / `.ui` и доменов OpenAI → `naive-out`, остальной Android Download Manager → `direct`; `route.final = naive-out`.

Исходные JSON ранее предоставлены владельцем. При диагностике найти и использовать фактические конфигурации из проекта/защищённого хранилища, сверить версии и правила; не реконструировать профили по этому описанию. Не копировать секреты или полные конфигурации в бэклог, Git и отчёты.

### Наблюдения

Скачивались бинарные вложения по 20 МБ непосредственно из ChatGPT.

| Среда | Daria | G3 Canary |
|---|---|---|
| Приложение ChatGPT, Wi-Fi | PASS | FAIL |
| Приложение ChatGPT, мобильная сеть | FAIL | FAIL |
| Chrome, мобильная сеть | Не проверено отдельно | PASS |

При FAIL приложение сообщает: «Произошла ошибка, попробуйте позже снова».

- Новый файл с новым именем также не скачивается.
- Принудительная остановка ChatGPT, очистка кэша и перезапуск не помогли.

- По сообщению владельца Canary ни разу не скачал файл в проверенных условиях приложения ChatGPT; отдельно в Chrome на мобильной сети зафиксирован PASS.

### Основная гипотеза

Специальное правило `Download Manager → direct` в Canary может отправлять загрузку ChatGPT вне VPN. Первое правило покрывает известные домены OpenAI, но фактическая загрузка может выполняться через другой домен, по IP или без доступного доменного имени при маршрутизации.

Альтернативные причины: Per-App SFA, различие Android Download Manager и внутреннего механизма загрузки ChatGPT, DNS, GeoSite/GeoIP, особенности мобильной сети.

**Гипотеза не доказана.** Отказ Daria в мобильной сети также требует объяснения.

### План быстрой диагностики

1. Проверить реальные конфиги Daria и Canary и порядок правил. Сохранить исходные копии в защищённом месте вне Git.
2. Подготовить отдельный временный **Canary-Test-1**: удалить только правило `Download Manager → direct`. Остальные настройки оставить без изменений.
3. Пользователь проверяет скачивание 20 МБ в приложении ChatGPT на Wi-Fi, где Daria уже показала PASS, затем на мобильной сети, и сообщает результаты.
4. Подготовить отдельный **Canary-Test-2**: убрать оба правила Download Manager, сохранив остальные настройки исходного Canary. Использовать для следующей проверки при FAIL первого варианта; повторить Wi-Fi и мобильную сеть.
5. Если FAIL сохраняется, сравнить Canary-Test-2 с Daria и проверить GeoSite/GeoIP, DNS и фактическую маршрутизацию через логи SFA.
6. Если нужны логи, временно повысить `log.level` до `debug` в тестовом профиле; установить, какое приложение инициирует загрузку, какое правило срабатывает и какой outbound выбирается, насколько это видно в логах. Перед публикацией удалить пароли, токены, подписанные URL и другие секреты.

**Первый шаг при взятии в работу:** сравнить фактические конфигурации и подготовить два тестовых JSON. Варианты независимо производятся от исходного Canary; безопасный diff должен подтвердить только оговорённые удаления правил. Пользователь самостоятельно импортирует тестовые профили и проверяет скачивание на Android. Подготовка файлов и тесты ещё не выполнены.

## BL-010 · Замечания к установщику

**Статус:** Зафиксировано, реализация отложена · **Дата:** 16.11.2026 · **Теги:** `UX` `INFRA`

### BL-010.1 · Повторный ввод IP серверов

**Источник:** ручная fresh-install приёмка владельца: после ввода SSH-адресов входа/выхода мастер снова требует те же значения в Q04 Entry public IPv4 и Q06 Exit public IPv4.

**Причина по коду:** native launcher уже получает SSH destinations в Q03/Q05 (`bootstrap/native-windows.ps1.in`, аналогичный macOS launcher), но `controller.configure` подставляет Q04/Q06 только из ранее сохранённой конфигурации. При fresh значения пусты; адреса первого шага не переиспользуются как defaults публичных IPv4.

**Результат:** сохранить данные первого шага в существующем контексте мастера и переиспользовать однозначно известные публичные IPv4. Для обычного пути с двумя явно введёнными публичными IPv4 не требовать повторного ручного ввода; показать адреса и роли в итоговом плане с возможностью исправления. Не вводить новый мастер или параллельный конфиг.

**Границы:** SSH destination и публичный/ожидаемый выходной IPv4 могут различаться (SSH alias, DNS, private IP, NAT, ProxyJump). Не назначать произвольный SSH hostname публичным IPv4 автоматически. Если публичный IP неизвестен, неоднозначен или отличается — задать понятный адресный вопрос с объяснением и доступным default. Сохранить текущие проверки адресов, маршрутизации и плана; не менять ноды в рамках этой записи.

**Предварительная приёмка:** Windows и macOS, fresh с двумя публичными IPv4 — каждый адрес вводится один раз, правильные entry/exit показаны в плане. Alias/DNS/private/NAT и нестандартный SSH-порт не приводят к молчаливому неверному public IP; уточнение/редактирование доступны. Resume/replacement сохраняют существующие адреса и роли. Текущий выпуск и серверы не изменять; исправление выполнить отдельным будущим пакетом.

### BL-010.2 · Дублируется вопрос Q02 об ID установки

**Источник:** владелец при ручном проходе видит Q02 дважды с одним и тем же вопросом об ID установки.

**Результат:** корректный ID спрашивается один раз и сохраняется между шагами существующего мастера. Повторный ввод допустим только при явной ошибке валидации или намеренном редактировании, с понятной причиной. Проверить границы native launcher/server wizard и повторные проходы configure/start/finish; точная причина дублирования пока не установлена, не считать исправленной.

**Предварительная приёмка:** обычный fresh-проход с валидным ID (например nh1) задаёт Q02 ровно один раз; просмотр/подтверждение плана, VPN commit и panel init не требуют его повторного ввода. Неверный ID объясняется перед повтором, редактирование остаётся доступным, resume использует существующий ID без изменения роли/реестра.

### BL-010.3 · Q16 обещает отложенный DNS, но fresh VPN+panel завершается ошибкой после Q20

**Источник:** вариант2 Q16 предлагает подготовить сервер сейчас и проверить после переключения DNS. После Q20 установка прерывается сообщением `Fresh VPN + panel requires DNS ready for trusted HTTPS; select ready at Q16`. Предупреждения о несовместимости выбранного варианта с fresh VPN+panel и понятного возврата к вопросу нет.

**Подтверждено по коду:** `client.QUESTIONS`/варианты Q16 описывают defer как доступный путь, а `controller.menu` после `configure` запрещает его для action=new/mode=fresh с панелью. Это несоответствие подсказки действующему ограничению, не доказательство допустимости установки панели без trusted HTTPS.

**Результат:** объяснять последствия непосредственно в Q16 для текущего сценария. Если ready обязателен — явно предупредить до выбора, что DNS должен указывать на вход для продолжения VPN+panel; не обещать установку при defer. При неподходящем выборе предложить переключить DNS и повторить проверку/вернуться к Q16 с сохранением остальных ответов либо явно выйти. Не обрывать мастер после Q20 без инструкции. Поддержку реального deferred-сценария рассматривать отдельно, если потребуется; не ослаблять проверку сертификата/TLS ради обхода ошибки.

**Предварительная приёмка:** ready и defer понятны до подтверждения; defer не вызывает неожиданного завершения через шаг; все уже введённые ответы сохраняются при возврате. При неподготовленном DNS нет ложного PASS, обхода trusted HTTPS или небезопасного развёртывания панели. Проверить сохранение работающего defer в применимых VPN-only/replacement сценариях.

**Общие границы BL-010:** это запись замечаний для будущего исправления. Изменения кода установщика, release bundle и текущих серверов сейчас не выполнялись; пункты не закрыты.

### BL-010.4 · Fresh VPN установлен, panel init отказал из-за lock0644

**Источник:** F3 владельца16.11.2026, rc2: после P01–P03 `vpnctl exit5`, panel setup incomplete; общий финальный текст не объясняет этап и ошибочно намекает на active rollback timer. Readonly диагностика: root-owned `/run/lock/empire-vpn.lock`0644, panel DB/key/units отсутствуют; VPN manifest уже committed. Пароль владельца ещё не применялся.

**Причина:** controller создавал lock через open(a) при umask022; touch(mode0600) не меняет существующие права. Go registry init защищённо отклоняет0644. Ошибка установщика, пользователь не должен чинить permissions вручную.

**Исправление-кандидат:**7c7b679, общий fd-based helper в существующих lock callers, проверка root/regular/single-link/sameinode и fchmod0600 без замены файла; flock сохранён. Фиксированные имена panel этапов/exitcode без вывода секретного stderr; нейтральное финальное сообщение. Linux10 regressions PASS; реальный packaged Go отказ0644 и успешная инициализация после helper PASS. Итог rc3/публикация и повтор владельца фиксируются в PLAN. F3 пока не закрыта.

### BL-010.6 · Fresh-install: ранняя проверка контекста и подтверждаемая очистка пула компонентов

**Статус:** Зафиксировано, реализация отложена · **Дата:** 16.11.2026 · **Теги:** `UX` `INFRA`

**Источник:** владелец подтвердил, что входная VDS фактически не переустановилась. При повторном fresh rc3 мастер допустил ввод ответов, подтверждение APPLY и сохранение clients.json, а затем остановился на entry/prepare: `Installed component versions differ; explicit upgrade is outside v1`. На ноде остался пул компонентов с marker rc2. Поздний отказ при заранее обнаружимом состоянии неприемлем.

**Требование владельца:** fresh-install должен до начала установки проверять контекст обеих нод. При наличии прежнего пула компонентов — заранее предупреждать пользователя, показывать адрес/роль ноды, найденные версии, состав очистки и последствия, затем предлагать очистку этого пула как часть fresh-сценария. После явного подтверждения выполнить необходимую очистку и продолжить установку; при отказе завершить без изменений. Не начинать применение с известной несовместимостью, чтобы затем гарантированно оборваться на prepare.

**Границы будущей реализации:** сначала readonly inventory/preflight до записи пользовательского реестра и APPLY. Перечень удаляемых установщиком файлов/каталогов/компонентов должен быть конкретным и проверяемым по существующим manifest/journal; нельзя считать любой обнаруженный файл принадлежащим установке. Явно определить, остаётся ли состояние VPN/панели и совместимо ли оно с продолжением fresh; если требуется более широкая очистка, показать её отдельно до выполнения, не оставлять следующую предсказуемую коллизию. Сохранять административный SSH-доступ, не затрагивать посторонние данные или резервную ноду. Не отключать integrity/version/writer guards ради продолжения. Это сценарий чистой установки с предупреждением и подтверждением очистки, не молчаливое обновление существующей установки. Переиспользовать существующие мастер/lock/journal/rollback.

**Предварительная приёмка:** обе чистые ноды проходят обычный fresh; оставшийся пул старого выпуска и различающееся состояние entry/exit обнаруживаются до записей и APPLY. Владелец видит точные ноды/версии/состав очистки; отказ ничего не меняет, подтверждение запускает объявленную очистку и последующую установку. Изменённые/непринадлежащие установщику файлы и несовместимое оставшееся состояние дают раннее понятное сообщение, а не поздний отказ. Новые SSH-сессии сохраняются; пользователь не должен вручную удалять marker или угадывать каталоги очистки.

**Текущая область:** только запись замечания. Очистка серверов, реализация reset/fresh и изменение опубликованного rc3 этим пунктом не выполняются и не разрешаются.
