# Реестр панели — W2

Текущий шаг и отметки о завершении ведутся в [плане разработки](PLAN.md).

В ветке разработки также сохранена форма входа владельца для W7. HTTP-тесты проверяют вход, выход и отказ при повторном использовании отозванной сессии. Подключение формы к приватному HTTPS-пилоту и проверка с телефона отложены до W7.

Внутренний пакет `internal/storage` ставит создание пользователя в очередь. Вызывающий код передаёт аутентифицированного оператора, ключ идемпотентности, логин, отображаемое имя, ревизию шаблона и целевой клиент. Операция возвращает идентификаторы пользователя и операции. Для вызова требуется заранее одобренная ревизия включённого шаблона.

Одна SQLite-транзакция `BEGIN IMMEDIATE` записывает пользователя в состоянии `provisioning`, сгенерированный пароль под AES-256-GCM, текущую версию реквизитов, привязку профиля и операцию `queued`. При повторе с теми же оператором, ключом и параметрами возвращаются прежние идентификаторы. Изменение параметров при том же ключе даёт `ErrIdempotencyConflict`. Ключ vault подаётся вызывающим кодом и живёт вне SQLite. Переход из `queued` в `succeeded` и из `provisioning` в `active` потребует отдельного исполнителя и проверки Caddy.

## Хранение и восстановление

Для предварительной сверки файлов v0.3.6 из корня репозитория выполните `python inspect_legacy.py <каталог-снимка>`. Подготовьте закрытую согласованную копию `auth.caddy`, `manifest.json`, `clients.json`, `master_user.sfa.json` и всех имеющихся `vpn-*.json` в одном каталоге с чувствительностью к регистру имён. Присутствующие `pending.json` и `user-rollback.json` также включите в копию. Храните снимок вне Git.

Команда читает файлы и выводит JSON со счётчиками расхождений и SHA256 поколения снимка. Код выхода 0 означает совпадение проверенных данных, 1 — требуется решение по расхождениям или коллизиям регистра, 2 — сверка невозможна. Отсутствие отдельного персонального профиля допускается. Полнота копии и актуальность работающего Caddy требуют отдельной проверки перед импортом.

Чтобы сохранить результат, укажите существующий приватный реестр схемы v3. Используйте путь к базе вне каталога снимка. Первый вызов возвращает `run_id`. Подставьте его во вторую команду.

```sh
python inspect_legacy.py "$SNAPSHOT" --registry "$REGISTRY"
python inspect_legacy.py "$SNAPSHOT" --registry "$REGISTRY" --plan "$RUN_ID"
```

План перечисляет точные логины для импорта в staging, роль и защиту мастер-пользователя, действия с профилями и Caddy и способ отката до переключения. При каждом запросе плана команда заново сверяет файлы. Для того же поколения она возвращает сохранённый план. Расхождения требуют разбора; при обнаружении другого поколения команда помечает прежнюю запись устаревшей и требует новой сверки. Нечитаемый или неполный снимок даёт код 2. Записи пользователей и выдача VPN-доступа относятся к отдельному шагу применения.

Для переноса в отдельную подготовленную базу staging сформируйте и проверьте план в этой же базе. На Linux выполните команду с путём к соответствующему бинарному ключу vault (32 байта, права 0600). Для версии ключа, отличной от 1, укажите `--key-version`.

```sh
vpnctl migration execute --approved-plan "$RUN_ID" --staging-db "$REGISTRY" --snapshot "$SNAPSHOT" --vault-key-file "$KEY_FILE"
```

Для первого переноса таблица пользователей должна быть пустой. После сверки поколения одна транзакция записывает пользователей в статусе `provisioning`, зашифрованные реквизиты, привязки и квитанцию. Успешный повтор возвращает тот же `operation_id`. Результат `staged` означает готовность записей в staging. Переключение владельца записи, рабочий Caddy и существующие профили относятся к W3.

У `vpnctl migration execute` успешный ответ по умолчанию и с `--json` содержит `operation_id` и `staged_users`. При ошибке с `--json` команда возвращает объект `error` с полями `code`, `message` и `retryable`. Режим `--quiet` подавляет успешный вывод. Коды завершения для этой команды:

| Код | Значение |
|---:|---|
| 0 | Перенос зафиксирован либо возвращена квитанция предыдущего выполнения |
| 2 | Ошибка аргументов, неполный снимок или неизвестный план |
| 4 | Конфликт состояния либо устаревший снимок (`CONFIG_DRIFT`) |
| 5 | Невозможно открыть реестр или использовать его ключ |
| 9 | Внутренняя ошибка или ошибка записи результата |

У клиента `operation show` ответ OPS-02 содержит `meta.request_id` и время в UTC. При отказе доступа к базе во время обновления сессии API возвращает HTTP 503 с кодом `DEPENDENCY_UNAVAILABLE` и `retryable: true`.

- Драйвер SQLite закреплён через go.mod/go.sum. Пакет открывает приватный каталог с WAL, foreign keys, synchronous=FULL и ожиданием занятого writer. Права базы и существующих sidecar-файлов проверяются до открытия на Linux.
- Нумерованные миграции встроены в сборку. История хранит SHA256 текста каждой миграции. Версии, контрольные суммы и подлинность ключа проверяются при открытии. Обновление v1 с уже записанными реквизитами требует успешной расшифровки всех прежних записей; смена рабочего ключа — отдельная будущая операция.
- Внутренний `OpenForPurpose` читает только текущие неотозванные реквизиты. Для подготовки записи Caddy допустимы статусы `provisioning` и `active`, для профиля — `active`, для повторного включения с прежним паролем — `disabled`. Неизвестная цель отклоняется до чтения базы. Вызывающий код выбирает цель внутри исполнителя и очищает результат после использования.
- `UpdateEffectiveStateCAS` фиксирует подтверждённый исполнителем результат по ожидаемой версии записи. Обычный путь: `provisioning → active ↔ disabled → deleting → deleted`. При удалении сохраняется время и точный логин. Любое промежуточное состояние допускает переход в `reconcile_required` при неопределённом результате. Служебная запись защищена от этого метода; выход из `reconcile_required` требует решения восстановления.

### Соответствие внутренних контрактов §5.8

| Контракт | Реализация и граница этапа |
|---|---|
| Пользователи | `UserRepository` читает и перечисляет метаданные, меняет имя и состояние по версии. `QueueCreate` резервирует логин и записывает операцию одной транзакцией. |
| Реквизиты | Генерация нового секрета встроена в `QueueCreate`. `vault.Encrypt` шифрует с привязкой к записи; открытие реестра проверяет ключ. Для чтения действующего секрета исполнитель указывает цель. |
| Операции | Создание с ключом идемпотентности входит в доменную транзакцию. `OperationJournal` записывает шаги, переходы и находит прерванную работу по SQLite. |
| Системное применение и профили | Исполнение контракта Caddy проверяется на W4, рендеринг и совместимость профилей — на W6. Проверки W2 используют отдельную базу и охватывают хранение. |

## Проверки

Из каталога модуля на Linux с Go 1.24+ и C-компилятором выполнить `go test ./...`. Проверки создают базы в приватных временных каталогах и используют синтетические ключи.

| Сценарий | Критерий |
|---|---|
| Две независимые SQLite-сессии одновременно создают пользователя с одним ключом | Совпадают идентификаторы; по одной записи пользователя, реквизитов, привязок и операции |
| Тот же ключ, другой целевой клиент | Конфликт без изменения данных |
| Дочерний процесс завершается до COMMIT | При новом открытии все пять таблиц пусты; повтор создаёт ровно один комплект |
| Дочерний процесс завершается после COMMIT до передачи ответа | Повтор возвращает исходные идентификаторы, пароль доступен для расшифровки |
| Проверка хранения | Реальный для теста сгенерированный пароль расшифровывается и ищется в непустых DB, WAL и SHM. Контрольный ID присутствует и в DB, и в WAL |
| Открытие с чужим ключом, изменение хеша миграции, общий каталог Linux | Открытие отклоняется |
| Переход заполненной v1 на v2 | Чужой ключ оставляет версию 1. Верный ключ сохраняет исходный пароль и записи |

Это проверки аварии процесса и содержимого конкретных файлов. Устойчивость при потере питания и полный бюджет диска панели требуют отдельных испытаний. Реестр не подключён к боевым Caddy или клиентским профилям.

## Чтение операции (OPS-02)

Внутренний Go-интерфейс `OperationJournal` хранит ход работы исполнителя. `Transition` меняет ожидаемый статус в SQLite; при одновременном захвате операции только один исполнитель переводит её из `queued` в `running`. Отмена разрешена из очереди. Успех фиксируется после `verifying`, результат отката — после `rollback_running`.

`AppendStep` принимает номер завершённого шага, ожидаемую фазу, имя этапа, результат, время и при наличии хеши или код ошибки. Нумерация начинается с 1. Точный повтор уже записанного шага допустим, пропуск номера и подмена записи возвращают конфликт. Время начала и окончания операции записывается при переходах состояния.

После открытия базы исполнитель может вызвать `FindUnfinished` для чтения операций в состояниях `running`, `verifying` и `rollback_running`. Для каждой записи возвращается последний номер шага (0, если шагов ещё нет). Дальнейшее решение требует сверки фактического состояния. Подключение этого чтения к запуску исполнителя относится к этапу его реализации.

Локальный `vpn-control` читает операции и записывает состояние административных сессий в существующий реестр SQLite. Сборка и запуск из корня Go-модуля в Linux:

```sh
go build -o ./vpn-control ./cmd/vpn-control
go build -o ./vpnctl ./cmd/vpnctl
./vpn-control -db /var/lib/vpn-control/state.db -socket /run/vpn-control/api.sock
```

Каталоги сокета и базы должны существовать с правами 0700, файл базы — с правами 0600. Один раз на узле панели создайте владельца в инициализированном реестре. Команда запросит отдельный пароль панели через `systemd-ask-password`. Повторное создание владельца блокируется.

```sh
./vpn-control -db /var/lib/vpn-control/state.db -bootstrap-owner owner
```

Для работы через SSH выполните следующие команды в оболочке пользователя с доступом к сокету. Подставьте существующий закрытый каталог для файла сессии. Для другого пути сокета задайте `VPNCTL_SOCKET`.

```sh
install -d -m 700 "$HOME/.vpnctl"
export VPNCTL_SESSION_FILE="$HOME/.vpnctl/session"
./vpnctl auth login owner
```

Сессия действует до 12 часов и истекает через 30 минут бездействия. Команда `./vpnctl auth logout` отзывает текущую сессию и удаляет локальный файл. Остальные устройства сохраняют доступ. Записи старого тестового формата без времени последней активности требуют повторного входа.

12 ноября 2026 года `go test -v ./...` прошёл в изолированном процессе на входной ноде с временной базой. Проверены вход через CLI, чтение своей операции, выход и отказ при повторном использовании сохранённой cookie. Отдельно проверены вторая активная сессия, оба срока действия, ограничение попыток входа, проверки Origin и CSRF. Четыре успешных входа через HTTP-обработчик заняли 68–83 мс с Argon2id (32 МиБ, два прохода, один поток). Проверка через браузер телефона предстоит после подключения формы входа.

```sh
vpnctl operation show <operation_id>
vpnctl operation show <operation_id> --json
```

Подставьте UUID из квитанции создания. CLI обращается к `GET /api/v1/operations/{id}` с cookie `session` через Unix-сокет. После переподключения можно повторить ту же команду. В ответ входят сохранённое состояние, упорядоченные этапы, коды ошибок и время. Режим `--quiet` подавляет обычный вывод. Успешное чтение возвращает код выхода 0, включая чтение записи со статусом `failed`; исход операции указан в поле `data.status`.

Сервер сверяет SHA256 токена с записью активной сессии и проверяет владельца операции в одном снимке SQLite. Чужая и отсутствующая операции дают одинаковую ошибку 404. Для истёкшей или отозванной сессии и отключённой административной учётной записи возвращается 401. В HTTP-ответ не включаются ключ идемпотентности, содержимое конфигурации, хеши и пути к снимкам. Ключ vault для чтения статуса не требуется.
