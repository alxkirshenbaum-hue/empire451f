**Тип:** адресное изменение требований и критериев завершения; **не замена LLD**  
**Версия:** 1.0 · **Дата:** 15.11.2026  
**Назначение:** агенту-архитектору для точечной интеграции в рабочие W-пакеты, гейты и план SOL Lead  
**Исходники:** `VPN_Control_LLD_Spec_Agent_v1.1.md` (прежде всего §5.7, §8–13), `VPN_Control_Architecture_Roadmap_Agent_v0.2.md`; стратегия — `VPN_Control_Change_01_Strategy_U_E_v1.0.md`.

> **Нормативное правило:** в пределах приоритизации и объёма пакетов настоящий CR предлагает заменить формулировки LLD v1.1; для **неизменяемых инвариантов**, схемы данных, контрактов методов, ролей и безопасности действует LLD v1.1, пока архитектор не представит согласованный минимальный diff. ## 0. План интеграции вместо полной переработки LLD

Внести **минимальные изменения** в:

- **LLD §12.1–12.3:** U-first / E-second, новые подгейты, добавление W9.5 сразу за W9, определение U/E PASS, прогресс по двум шкалам.
- **LLD §5.7 и §8:** уточнить отличие *portable user export/import* от *полного disaster recovery*; сохранить общие интерфейсы BKP, но уточнить обязательность/приоритет и добавить, если нужно, узкие интерфейсы переносимого импорта.
- **LLD §9 и §13:** оставить минимальную security floor и тесты целостности для U; ресурсные/проверочные матрицы классифицировать U/E с учётом риска и уже пройденных доказательств.
- **LLD §10–11:** разделить user-visible capabilities на U и расширенные методы на E; не менять wire protocols / текущие server paths.
- **Roadmap v0.2:** обновить только последовательность релизов и краткую приоритизацию, **не** переписывать архитектурные принципы.
- **Рабочие документы агента:** актуальный `BACKLOG`, `HANDOFF_W8_CONTINUED_2026-11-15.md`, gate reports W8/W9/W9.1, actual Git files. Их содержимое надо прочитать; этот CR не подменяет сведения о существующем коде.

Сначала архитектор составляет `source_id ↔ WnU/WnE ↔ tests ↔ status ↔ evidence`. Старые G8/G9 остаются трассируемыми parent-gates, а не исчезают. Если в текущей схеме несколько ворот объединены, дать их фактическую нумерацию.

## 1. Общая система критериев

### U-gate

**U-PASS =** конкретный пользовательский сценарий выполнен end-to-end + минимальные необходимые негативные/аварийные проверки + security floor + отсутствие значимой регрессии. Нельзя закрыть U по библиотечным unit PASS, если пользовательский сценарий отсутствует.

**Security floor для всех U, в объёме затронутого функционала:**

1. Административные действия требуют подтверждённой роли владельца; UI/API не публичны, обычный VPN-пользователь не получает admin права; путь SFA → panel HTTPS с корректным TLS либо честный BLOCKED по требуемому UX.
2. Секреты при хранении/экспорте/передаче не доступны посторонним, не попадают в логи/репозиторий; нельзя экспортировать plaintext JSON пароли без защищённого контейнера.
3. Нельзя потерять/испортить рабочие записи Caddy, клиентские профили или `master_user`; старые логины case-sensitive; управление через общий writer/lock.
4. Mutating операции имеют понятный результат, валидируют вход, не оставляют неопределённое состояние и позволяют возврат к известной исправной точке, когда возможен ущерб данным.
5. Действующий data plane независим от панели; без новых обходов firewall/namespace/WireGuard fail-closed; изменения нод — staging и отдельное production approval.
6. Ограничение памяти нового управления — ≤500 000 000 байт на обеих VDS в сумме, по правилам §2.4/§11.4 LLD; измерять у новых процессов, не подменять только RSS API.

**E-gate:** все остальные исходные требования/тесты, полезные улучшения и расширенные сценарии. Обязательное ранее правило security не переносится в E только потому, что проверка сложна. При конфликте классификации архитектор показывает точный риск, реальную зависимость и минимальный тест U.

**Статусы:** `U_PASS`, `U_FAIL`, `U_BLOCKED`, `U_INCOMPLETE`, `U_DEFERRED_BY_OWNER`; отдельно `E_PASS`, `E_PASS_REUSED`, `E_FAIL`, `E_INCOMPLETE`, `E_NOT_RUN`, `E_DEFERRED_BY_OWNER`. Счётчики считать только по явно названным U/E-критериям, не смешивать с числом старых G8 checks.

**Качество evidence:** SHA коммита/бинарника; дата; имя среды (`staging`, `local`, `production`); реальный или synthetic источник; sanitized артефакт/лог; что действительно доказано; применимость к текущему коду. Evidence можно использовать повторно только если не изменена затронутая область.

## 2. W8 — экспорт, перенос и восстановление пользователей

### W8U: пользовательская цель

> Владелец нажимает «Экспорт пользователей», получает **переносимый зашифрованный архив**. После установки VPN Control на новую пару VDS он импортирует архив, видит тот же список пользователей и может подключиться с прежними реквизитами; прежние SFA-профили продолжают работать, **если** сохранены необходимые параметры подключения и корректно переведён endpoint.

**Важно:** backup для восстановления той же системы и portable export на другой хост **не одно и то же**. Локальная DB с ключом, который существует только на старой VDS, **не считается переносимым экспортом**. Архитектор должен выбрать минимальный механизм контролируемой упаковки/переноса ключевого материала (например, экспорт с отдельным паролем владельца), без введения универсальной PKI/DR-платформы.

**Минимальный набор функций:**

- `W8U-01 Export`: создать и скачать защищённый bundle всех обычных пользователей и защищённого `master_user` в его корректной роли; включить exact-case login, authentication secret, enabled/revoked status, связи с шаблоном/доменом и все данные, **реально необходимые** для восстановления аутентификации. Не экспортировать административные сессии как активные авторизации.
- `W8U-02 Verify`: проверить формат/версию bundle, checksum/authenticity, успешную расшифровку/совместимость схемы, без логирования секрета; отказ на неверный пароль/повреждённый файл.
- `W8U-03 Import`: в **новую чистую** установку выполнить preview и импорт. Дедупликация/конфликты логинов case-sensitive; при существующем пользователе не перезаписывать пароль молча, не удалять Caddy-only пользователя, не менять `master_user` неявно. После импорта SQLite, Caddy, export/manifests и профильные ссылки согласованы.
- `W8U-04 Working VPN / failure safety`: проверить реальную авторизацию старого клиента (fresh TCP и UoT v2); проверить disabled/revoked; при повреждённом bundle/ошибке применения новая инсталляция остаётся пригодной и не теряет уже имевшихся записей. Источник экспорта не меняется и не зависит от успеха импорта.

**Оговорка старых профилей:** если новый ingress имеет другой домен/порт/сертификат/параметры Naive, один лишь перенос паролей не гарантирует работу прежнего JSON; приёмка использует сохранённый домен и корректный DNS/TLS/transport. При смене endpoint фиксировать необходимость переиздания профиля, а не объявлять импорт «сломавшимся».

**Минимальные acceptance:** до W9.5U допустима вручную подготовленная **чистая staging-инсталляция панели** для проверки переносимости; W9.5U затем автоматизирует создание такой инсталляции общим установщиком. Один реальный полный export/import на изолированных данных; одинаковое число и идентичность аккаунтов; старый клиент подключается; revoked не подключается; corrupted export отклонён, state destination корректен. Наличие удобной кнопки/CLI подтверждается, но API-only encrypted backup без механизма *import to fresh install* — **не W8U PASS**.

**Маппинг LLD:** `BKP-01`, `BKP-04–06` (узкий переносимый сценарий), `USR`, `CRED`, `PROF`, `MIG`, §3/§6 и E1-SC-07; архитектор обязан определить, хватает ли существующих методов или требуется `EXP-*/IMP-*` alias/contract. Не выдумывать новый параллельный writer.

### W8E: перенести и зачесть по evidence

- Полное recovery всей DB/runtime с сохранением истории/audit и системой restore-plan `BKP-05/06`, включая сложные destination-state/rollback cases.
- Ротация копий ключей (например, `1→2→3`) и отрицательные сценарии, отдельные workflows активации/переключения ключа.
- ACL/xattrs roundtrip, расширенная политика архивного wrapper, «редкие» файловые/permissions edge cases.
- `BKP-02/03/07`: листинг расширенной истории, prune/retention policies, archive audit, recovery runbooks сверх переносимого сценария.
- Глубокие повторные fail-injection, cold reboot/load/soak и независимый расширенный security review, если не выявлен блокирующий safety дефект.

**Статус по отчёту агента 15.11 (предварительно, не принимать без проверки):**

| Проверка | Как классифицировать до сверки кода |
|---|---|
| Owner API + encrypted backup штатным worker | `U partially implemented`; отдельные PASS можно зачесть в E |
| Offline verification и подготовка restored DB; sessions cleared; history/audit preserved | `U partial` + `E_PASS_REUSED` по подтверждённым check |
| Copy-only key rotation 1→2→3 и negative scenarios | `W8E candidate E_PASS_REUSED` |
| ACL/xattrs roundtrip, wrapper policy | `W8E candidate E_PASS_REUSED` |
| Restored Caddy/API, owner login, unchanged client profile, fresh TCP/UoT, revoked fails | `U partial end-to-end evidence`, подтвердить конкретный переносимый bundle/endpoint |
| Readonly restore-plan helper, **не полный CLI** | `E_INCOMPLETE` |
| Исправление rollback `8708435`, проверка прервана из-за существовавшего scratch path | `E_NOT_VERIFIED` до recovery-only теста |
| Prune/audit uncommitted, uncompiled, untested WIP | `E_INCOMPLETE`; изолировать, не считать PASS |
| Independent review / pinned full suite ещё впереди | `E_NOT_RUN`, кроме известных критических дефектов |

**Нельзя:** удалять уже полезный E-код, молча «закрывать W8» по отчётам без `U-01..04` или повторять всё с нуля. Нельзя `git reset --hard` на WIP без сохранения.

## 3. W9 — функциональный выпуск MVP

### W9U: что получает пользователь

> Владелец на телефоне через SFA открывает HTTPS-панель, видит корректную базу пользователей, создаёт/блокирует/меняет/удаляет пользователя, получает SFA-профиль, экспортирует и импортирует пользователей; базовая работоспособность VPN не меняется.

**Минимальные acceptance:**

1. Owner login и права: обычный VPN-пользователь не может управлять панелью; извне без VPN доступ к админке закрыт; TLS валиден по выбранной схеме. Если целевой UX `panel.home.arpa` не работает, `W9U_BLOCKED`, а не объявлять SSH-only полноценной приёмкой.
2. Один сквозной цикл UI/CLI: create → скачать рабочий профиль → проверить connection → disable → запрет нового auth → enable/rotate/delete по согласованному сценарию; другие пользователи не теряются, перерыв Caddy честно указан.
3. W8U export/import доступен владельцу, базовый health разделяет фактически живой сквозной egress и прошлый локальный audit egress. Не показывать фиктивный `online`/нулевую статистику.
4. Устойчивый перезапуск панели/двух нод без утраты пользователей и без зависимости VPN data plane от панели; корректный известный rollback при ошибке изменения учётных данных.
5. Общий небольшой regression set на реально затронутый код; финальный наблюдаемый пользовательский сценарий оформлен в отчёте.

**Технические границы:** W6/W7 текущие статусы по последнему отчёту `3/4` и `3/4`. Не скрывать незакрытые условия: архитектор должен объяснить, какие из них реально блокируют U, а какие являются расширенными и уходят в E. Совместимость SFA версий/Canary Download Manager не объявлять PASS без измерений; при неподтверждённой версии пометить ограничение выдачи и предъявить владельцу решение.

### W9E: дополнительные релизные требования

Широкая staging-canary rollout matrix, многочасовые load/soak, все редкие fault-injection, расширенные runbooks/подписи отчётов, дублирующие security-аудиты и повторные дриллы без изменения соответствующего слоя. **Не** переносить в E реальный критический дефект безопасности, сбой миграции, отсутствие recovery при пользовательской операции или нарушение 500 MB.

**Маппинг:** LLD §12.2 `W9-E1-Release`, §12.3/§13; обязательные E1 `USR/CRED/PROF/SYS/OPS/AUD/BKP` методы сохраняют контракты, классификация gate меняется, а не сами интерфейсы.

## 4. W9.1 — не описан в LLD v1.1: требование на реконсиляцию

В рабочем отчёте агента присутствует `W9.1 0/6`; **неизвестно**, какие именно шесть условий туда входят. Запрещено приписывать ему выдуманную функциональность.

**Действия архитектора:** найти актуальный `BACKLOG`/план/коммиты, выписать все шесть gates и владельцев, проверить дубли W8/W9/W9.5, затем либо:

- разложить по `W9.1U` (только необходимый пользовательский сценарий/critical safety) и `W9.1E` (дополнительные проверки); либо
- убрать отдельный пакет, **сохранив трассировку каждого из шести пунктов** в W9U/E или W9.5U/E.

Принцип: нельзя сделать искусственный W9.1 между релизом MVP и установщиком, если он не несёт обязательной зависимости. Любой новый блокер — с конкретным доказательством.

## 5. W9.5 — ДОБАВЛЕННЫЙ пакет, сразу после W9U

### W9.5U: существующий установщик разворачивает **полный MVP комплекс**

> Один запуск проверенного установочного сценария на двух чистых VDS выдаёт рабочую цепочку VPN **плюс** панель E1 с SQLite, контролем пользователей и готовностью импортировать W8U bundle. Аналогично предусмотрено добавление панели к существующей рабочей паре без потери пользователей.

**Обязательные пользовательские сценарии:**

1. **Fresh pair:** существующий установщик v0.3.6 или его контролируемая эволюция: ingress + egress + panel binary/UI/API + storage/migrations/secrets + systemd + настроенный путь владельца через SFA, без ручной ручной «доустановки» компонента панели.
2. **Upgrade existing pair:** на уже работающих VDS появляется панель, прежние логины/пароли/`master_user`/профили не теряются; существующий installer/CLI и панель используют единый writer/lock.
3. **Portable migration:** после fresh pair импорт из W8U, owner login, старые credentials, fresh TCP/UoT через новую пару, check revoked.
4. **Replace ingress:** действующий режим замены входа сохраняет exit VDS, защитную политику и нужные учётные записи/панель; разрешённые точечные изменения WG peer/SSH allowlist как в LLD §11.3, без обещания byte-identical egress.

**Acceptance:** минимальный воспроизводимый запуск fresh и один upgrade/migrate на staging; подтверждённый owner login/профиль/TCP+UoT, read-only audit, перезагрузка без дефекта запуска и безопасная обработка ошибки. Для replacement при отсутствии отдельной staging-пары сохранить реальный тест существующего скрипта как ранее подтверждённый evidence и отдельно проверить включение панели; не подменять staging реальным production без разрешения.

**Уточнения:** SSH reuse/new key — существующие режимы установщика, их не переписывать; не копировать private owner SSH key на ingress. Источник данных migration/export не должен быть только локальным DB-файлом с непереносимым ключом. В установке не принуждать обновление Caddy/WG/sing-box без технической необходимости.

### W9.5E

Расширенная compatibility matrix существующих дистрибутивов, многократные destructive/install/reboot/rollback drills, полноценный update/rollback packaging framework, редкие версии legacy, автоматизированные матрицы upgrade/cleanup и расширенное подтверждение безопасности установщика. Часть уже выполненных installer tests можно зачесть.

**Ограничение:** необходимые preflight, защита секретов, работающий rollback при неудачной миграции и проверка конфигурации остаются в W9.5U. Лимит RAM — действующий, включая установочные процессы согласно LLD; если недостижим в конкретном сценарии, предъявить владельцу измерения и варианты вместо самовольного ослабления.

## 6. W10 — базовый мониторинг

### W10U: информативный экран состояния

1. Видно: ingress/egress roles, состояние Caddy/sing-box/WG, актуальный end-to-end TCP/UDP probe, выходной IP; для CPU/RAM/disk ingress — только измерения с реальным источником.
2. Для egress **раздельно**: online сквозная доступность и `last local audit` с timestamp/staleness, без фантазий о live CPU/disk; не переносить приватный SSH-ключ владельца на ingress.
3. Видно состояние и свежесть последнего аудита/backup, явные `unknown/stale/not measured` вместо `0`/`offline`.
4. Базовые метрики контроллера и измеренное потребление памяти в пределах лимита. Никакого тяжёлого per-user packet capture.

**Acceptance:** один живой корректный PASS и один управляемый FAIL/stale с понятным обновлением UI/CLI. Если отдельная метрика недоступна — честное `unsupported`, не блокирует весь базовый экран.

### W10E

`MET-02` точная byte-statistics по каждому пользователю после доказанной атрибуции, `MET-03` расширенная история подтверждённой auth-активности, `MET-04/05` источники/confidence/trends, sampling/retention/downsampling `metric_samples`, сложная проверка UoT attribution, более длинное хранение и read-only live egress channel **только по отдельному дизайну**. Не придумывать «online» или per-user bytes из общего WG.

**Маппинг:** LLD §10, `MET-01..05`, §2 RAM, `SYS`/`AUD` существующие методы; допустима частичная реализация отдельных MET из U и E без переименования API.

## 7. W11 — уведомления

### W11U: 1 канал + несколько критичных событий

1. Владелец выбирает **один** подтверждённый канал уведомлений (Telegram предлагается как простой вариант, но не утверждён по умолчанию).
2. Минимальные события: продолжительная недоступность ingress, нарушение сквозного выхода/WG, восстановление; при наличии надёжного источника — срок действия TLS. Не отправлять событие о каждом единичном сбое.
3. `Test notification`, enabled/disabled, базовая дедупликация/cooldown, безопасное хранение токена, отсутствие отправки секретов.
4. Оповещения не выполняют команды перезапуска/автолечения и не меняют сеть.

**Acceptance:** искусственно наблюдаемые fail → одно сообщение; recovery → сообщение; повторный fail в cooldown не создаёт лавину; без канала событие отражается локально.

### W11E

Настраиваемые `alert_rules`, подтверждение и история `alert_instances`, несколько notification targets, quiet hours, сложные пороги, routing/escalation, расширенная диагностика `DIA-01..03`, автоматические ограниченные probing jobs, длинное хранение.

**Маппинг:** LLD §10.2/10.4 `ALT-01..05`, `DIA-01..03`.

## 8. W12 — шаблоны SFA

### W12U: выбор уже проверенного шаблона

1. Панель показывает небольшой каталог **одобренных** шаблонов: название, версия клиента, назначение (Clean/Split), совместимость и известные ограничения.
2. При создании пользователя/повторной выдаче можно выбрать шаблон и получить валидный персональный JSON без изменения серверной конфигурации.
3. Действующие уже выданные профили не изменяются автоматически; неподтверждённый Canary не продвигается в обязательный default.
4. При несовместимой версии SFA — отказ/предупреждение вместо профиля, который валидируется только более новым ядром.

**Acceptance:** 1–2 проверенных шаблона, одна выдача в UI и корректная связь с пользователем, повторный импорт работает; отдельно не объявлять решённой проблему Android ChatGPT Download Manager из бэклога без тестов на Wi-Fi и mobile.

### W12E

Полный редактор шаблонов/JSON, создание и promotion immutable revision `TPL-04..06`, diff/version UI, automatic compatibility matrix, массовая перевыдача `BULK-01/02`, подписки `SUB-01..03` с отдельной моделью угроз и opt-in, сложные client-specific variants.

**Маппинг:** LLD §7, §10, `PROF`, `TPL`, `SUB`, `BULK`.

## 9. W13 — запуск существующего deploy из панели

### W13U: ограниченный адаптер существующих скриптов

1. В UI/CLI выбрать **один из уже поддерживаемых режимов** (fresh pair / replace ingress) и увидеть параметры, последствия и необходимые предосторожности; никаких произвольных SSH-команд.
2. У владельца есть preview/dry run и явное подтверждение; запуск только разрешённого сценария, через существующий script interface с ограниченными правами и штатными логами.
3. Отображаются результат, стадия выполнения, ошибка и способ безопасно продолжить/вернуться к известному состоянию; защитные инварианты не меняются.
4. При превышении RAM или невозможности безопасно запустить из UI честно показывается `unsupported_due_to_memory_budget` **с рабочим внешним CLI/runbook**, без ложного `W13U_PASS` на функцию GUI execute. Объём «безопасного execute» согласовать с владельцем, если требуется отдельный режим.

**Acceptance:** один allowlisted сценарий на staging, невозможность произвольного ввода команд и изменение целевой ноды только после approval. Существующий installer с W9.5 не переделывать.

### W13E

Полная система `deployments`/`deployment_steps`/`planned_changes`/`approvals`, immutable plan/step journal, elaborate resumability, event streaming, дополнительные SSH/topology cases, расширенные матрицы memory/rollback и автоматизация под несколько хостеров.

**Маппинг:** LLD §11.1/§11.2 `DEP-01..08`, `NMG-01..04`, §11.4.

## 10. W14 — замена заблокированного ingress

### W14U: безопасное восстановление доступа через новую входную ноду

1. Владелец выбирает новую ingress VDS и existing exit, использует проверенный сценарий «заменить вход без замены выхода».
2. Предварительно показываются **точечные** возможные изменения exit: WireGuard peer/AllowedIPs, SSH source allowlist, связанные firewall/routes; нельзя обещать неизменность checksum всей exit.
3. Выполняется тест пути SFA → Caddy/CONNECT → sing-box → WG → прежний egress IP, TCP/UoT, авторизация старых пользователей; DNS/TLS и прежние профили сохраняются там, где это возможно.
4. Проверяется **новая SSH-сессия через новый ingress** до удаления старого доступа. Старый маршрут остаётся доступен для восстановления, пока новая цепь не принята.
5. Ошибка приводит к возврату к известному защищённому состоянию или остановке с явным manual recovery; никакого fail-open или разрушительного действия «продолжить любой ценой».

**Acceptance:** один end-to-end staging ingress swap с прежним exit/user login плюс intentional failure на критическом шаге с предсказуемым безопасным исходом. Использовать доказательства существующих тестов скрипта; не переписывать сам алгоритм без необходимости.

### W14E

Расширенная матрица хостеров/IP/SSH/WG, multiple peers, complex downtime minimization, detailed orchestration/approval chain, nested rollback сценарии и topology migrations за пределами стандартной замены ingress.

**Маппинг:** LLD §11.3 E3-SC-01, `ROUTE-01/02`, `DEP-05..08`.

## 11. W15 — advanced: только выбранная пользовательская ценность

### W15U

В исходном W15 смешаны **четыре самостоятельных продукта**: multi-ingress, egress replacement, роли дополнительных администраторов, recovery playbooks. Владелец не подтверждал, что все четыре нужны сейчас.

**Решение:** архитектор предлагает **минимум одну** конкретную пользовательскую историю (например, учёт второй входной ноды; замена egress; выдача доступа второму администратору) с оценкой зависимости и риска. **Не реализовывать её без выбора владельца.** При отсутствии выбора `W15U = DEFERRED_BY_OWNER`, а не ложный PASS и не блокировка завершения уже утверждённого полезного продукта. Разбиение W15U/W15E как структуры при этом сохраняется.

### W15E

Все оставшиеся улучшения W15, принятые владельцем: `ROUTE-03/04` egress replacement, `RBAC-01..04`, `AUTO-01/02`, `node_assignments`/`node_groups`, расширенный multi-ingress, feature-specific tests. Не объединять эти операции в одну опасную универсальную кнопку.

**Маппинг:** LLD §11.1/§11.2/§11.5.

## 12. Общая матрица U/E и новая последовательность

| Пакет | U-закрытие по продукту | E-пакет / тип переноса | Зависимость |
|---|---|---|---|
| W8 | Export → Import → Working VPN | DR/key/ACL/prune/extended restore | W3–W7; staging source/destination |
| W9 | Полноценная MVP-панель для владельца | Большая release/soak/regression matrix | W8U + фактические блокеры W6/W7 |

| W9.5 | Единый installer VPN+MVP, upgrade, import | Многовариантный deployment QA | W9U; W8U export |

**First pass:** W8U → W9U → optional W9.1U → W9.5U → W10U → W11U → W12U → W13U → W14U → W15U (только если выбран). **Second pass:** E-подзадачи с уже зачтёнными PASS и согласованным отложенным scope. Порядок E оптимизировать по зависимостям, не обязан быть строго числовым.

**Синхронизация установщика после W9.5U:** новое U-функциональное расширение E2/E3 должно входить в следующую версию дистрибутива без отдельной ручной установки. Разработку W13/14 это не заменяет.

## 13. Как переписать старые gates без потери тестов

В существующих gate-файлах не удалять строки `G8`, `G9`, `W9.1`, а сделать отображение типа:

```yaml
work_package: W8
original_gate: G8
new_gates:
  - id: W8U
    checks: [W8U-01, W8U-02, W8U-03, W8U-04]
    status: INCOMPLETE     # пример, не факт из Git
  - id: W8E
    checks: [copy_only_rotation, acl_xattrs, prune_audit, extended_restore]
    status: PARTIAL        # пример, E evidence подлежит сверке
traceability:
  source: VPN_Control_LLD_Spec_Agent_v1.1.md#5.7
  evidence: []
```

Для `W9.1` состав `checks` и mapping заполняется **только после чтения реального backlog**; не предполагать, что W9.1 — это installer integration. Новое обозначение установщика — `W9.5`.

**Запрет ложного прогресса:** `W8 0/4` из старого gate не превращается автоматически в `W8U 4/4`; доказать отдельные шаги. Аналогично уже пройденное E не надо стирать: сохранить `E_PASS_REUSED` с source SHA и без повторного исполнения.

## 14. Сокращённые тесты приёмки для U и границы E

| Область | U требует | E добавляет |
|---|---|---|
| Users/Caddy | 1 create/disable/rotate, проверка другого пользователя, rollback на критической ошибке | широкая 14-point fault matrix, дополнительные race cases, обширная нагрузка |
| Portable export | 1 encrypted export, integrity, import clean, old profile, revoked, reject corrupt file | extra key versioning, multiple destinations, full legacy historical restore |
| Panel | VPN owner login, non-admin denied, external denied, базовая доступность после restart | сложные браузерные cross-platform матрицы и prolonged soak |
| Installer | staging fresh+upgrade, новая панель и пользователей можно использовать, отсутствие fail-open | полная матрица OS/SSH modes и повторные destructive drills |
| Monitoring | live end-to-end + last audit distinction, one stale/fail case | точная per-user attribution и расширенное хранение |
| Alerts | fail/recovery и cooldown в одном канале | много каналов, generic rule engine |
| Templates | approved template can generate working profile | editor, subscriptions, batch publishing |
| Deploy/swap | one approved сценарий, short failure path и admin access preserved | множество провайдеров, complete orchestration/fault-matrix |

**В любой строке:** если найден критический дефект безопасности, реальная потеря credential/user, нарушение RAM или direct internet leak, U блокируется; не прятать проблему в E.

2. **Actual W8/W9/W9.1 status**: текущие git-ветки, HEAD, незакоммиченный prune/audit, реальные четыре G8 / четыре G9 / шесть W9.1; разложить каждый на U/E.

## 16. Решения, которые нельзя принимать за владельца

- Реальный состав `W9.1` и его судьба после трассировки.
- Нужен ли сейчас полноценный W15U и какой из advanced use cases действительно важен.
- Единственный канал уведомлений W11U (Telegram — предложение, не факт).
- Допустимые исключения из первоначальной поддержки SFA 1.14.4/1.15 alpha13 до завершения отложенной диагностики Download Manager.
- Любое изменение security invariants, памяти 500 МБ, состояния `admin off`, master_user, режима работы с SSH ключом, topology exit либо production deployment.

**Принцип решения:** сначала функция, потом расширенная инженерия; никогда — «сначала ослабить защиту ради скорости». Документы CR-01/CR-02 следует интегрировать как *дельту* к действующей v1.1 и актуальному проектному backlog с полной трассировкой.
