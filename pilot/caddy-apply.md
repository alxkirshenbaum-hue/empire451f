# G0b. Применение пользователей Caddy, 12 ноября 2026

## Решение

Для адаптера панели выбрать reload через закрытый Unix-сокет. Рабочая nh1 пока использует admin off и штатный restart. Переход на сокет требует отдельного плана: доступ к сокету даёт управление конфигурацией Caddy; создать приватный каталог, разделить системные идентичности Caddy и sing-box (сейчас обе службы используют evpn), дать доступ только Caddy и узкому привилегированному исполнителю, проверить невозможность подключения из Web UI, sing-box и клиентского proxy. Установщик должен учитывать изменение в своём манифесте. Первое включение сокета потребует согласованного перезапуска.

В интерфейсе операция отзыва должна обещать запрет новых подключений. Уже открытые TCP и UoT-ассоциации могут продолжать передавать данные. Для немедленного обрыва всех действующих потоков конкретного пользователя проверенного механизма пока нет. Существующий restart прерывает связь остальных пользователей и требует предупреждения, подтверждения и нового теста доступности.

## Измерения

| Операция | Restart: применение, с | Интервал между успешными новыми CONNECT, с | Reload: применение, с, два запуска |
|---|---:|---:|---:|
| Создание | 90,27 | 90,27 | 0,17 / 0,18 |
| Ротация | 90,11 | 90,46 | 0,12 / 0,06 |
| Отключение | 90,06 | 90,32 | 0,12 / 0,06 |

После каждого restart перестали отвечать все четыре прежних потока: TCP и UoT изменяемого и контрольного пользователя. Новые подключения разрешённых пользователей восстановились. 90 секунд — заданное в эксперименте ожидание завершения старого процесса с открытыми потоками, соответствующее наблюдавшемуся TimeoutStopUSec рабочей службы.

На обоих прогонах reload ни одна контрольная проба не пропала. Старые TCP и UoT продолжали передавать случайные контрольные сообщения, включая уже отключённую учётку. Новый CONNECT контрольного пользователя с отдельным TLS-подключением проходил на всём интервале; частота опроса около пяти проб в секунду. Это ограничивает точность вывода о непрерывности.

После ротации и отключения отдельный повторный тест пытался открыть новый TCP-поток через тот же клиентский процесс sing-box со старым паролем, затем через вновь запущенный процесс. Обе попытки отклонены в обоих сценариях. Новая попытка с неизменённой контрольной учёткой прошла. Доступ к другим адресам через ранее открытую UoT-ассоциацию отдельно не измерялся.

## Условия и повторение

Использованы Caddy SHA256 `7509cd6b38a5da3324a08f32f62a7000237e5e1f6ccfb58e818bf730de58d30c`, forwardproxy из github.com/klzgrad/forwardproxy (ревизия e747854e7874) и установленный sing-box. Временный systemd unit использовал DynamicUser, PrivateNetwork, PrivateTmp, ProtectHome, ProtectSystem=strict и NoNewPrivileges. Внутри namespace был только lo. Синтетические клиенты проходили Naive HTTPS → тестовый Caddy → HTTP CONNECT → тестовый sing-box → локальные TCP/UDP echo. Рабочие Caddy, профили, ключи и namespace в испытании не участвовали. Пиковое потребление всего тестового unit в первом прогоне — 66,3 МиБ по systemd.

Для повтора поместить `pilot/g0b.py`, `verify.py` и `templates/vpn-add-user` в доступный для чтения тестовый каталог на узле с теми же бинарниками в /opt/empire-vpn/bin. Запустить внутри изолированного unit команду `python3 -B g0b.py ./vpn-add-user`; необязательный аргумент `reload` запускает только второй вариант. Драйвер отказывается работать при наличии сетевого интерфейса, отличного от lo. Обычный путь выдачи вызывает функцию issue() из поставляемого скрипта с временными путями, непривилегированной записью и заменой systemctl на управление дочерним тестовым процессом. Ротацию и отключение моделирует изменение того же include. Условия не воспроизводят задержку WAN, поведение интерфейса Android и полный граф зависимостей рабочего systemd.
