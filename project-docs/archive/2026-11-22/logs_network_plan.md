## 2. Архитектура и сохранение SSH

Windows → kvmka-entry → hosth-exit по ProxyJump. Приватный ключ остаётся на Windows. Основные маршруты обоих хостов сохраняются через шлюзы провайдеров; SSH не зависит от WireGuard.

Пользователь → TCP 443 входа → фиксированный TCP-релей → Caddy с naive forwardproxy в отдельном network namespace → wg0 → HostHatch → NAT → Интернет.

Предлагаемые адреса (после проверки отсутствия конфликтов): WG 10.77.0.1/30 на выходе, 10.77.0.2/30 в пространстве прокси; veth 10.78.0.1/30 на входном хосте, 10.78.0.2/30 у прокси. TCP-релей (systemd-socket-proxyd, отдельные экземпляры 80/443) передаёт только к фиксированным портам Caddy на veth, без завершения TLS. Этот вариант скрывает исходный клиентский адрес от Caddy; учитывать при логировании и лимитах. Не разрешать релею произвольный CONNECT.

WireGuard-интерфейс создать в основном namespace входа и перенести в пространство прокси: UDP-сокет остаётся в исходном namespace, транспорт идёт через обычный маршрут хоста. В namespace прокси default route только через wg0; veth имеет только подключённую /30-сеть для ответов релею. На выходе AllowedIPs peer — только 10.77.0.2/32. На входном peer AllowedIPs 0.0.0.0/0 применяется только к пространству прокси. Не запускать автоматическую установку default route WireGuard в основном namespace входа.

DNS прокси — отдельный resolver-конфиг namespace с внешним DNS через wg0; не использовать DNS хоста через veth. ACME/обновление сертификата Caddy тоже через WG. При отказе выхода новые сертификаты временно не выдаются — это ожидаемо. IPv6 пользовательского выхода на первом этапе закрыт. IPv6 SSH хоста не менять без необходимости.

## 3. Firewall и fail-closed

Входной хост: INPUT default drop с loopback, established/related, необходимым ICMP и SSH; публичные TCP 80/443; ответы WG. SSH сначала сохранить доступным по текущему пути, не вводить ограничение динамическим IP ноутбука без проверки. FORWARD default drop: namespace не получает NAT/forward через ens3. Системный OUTPUT хоста сохраняет обновления, NTP и SSH ProxyJump; пользовательские назначения обслуживает только изолированный Caddy.

Namespace: разрешить новые входящие соединения с veth хоста только на 80/443 и ответы обратно; новые исходящие разрешить только на wg0. На veth запретить новые исходящие, включая DNS. Запретить IPv6-выход и обращения к служебным/локальным сетям, metadata и административным портам; ACL Caddy дополнить сетевыми правилами. Отсутствие wg0 не должно создавать альтернативного выхода. Защита должна сохраняться при отсутствии маршрута, перезапуске и загрузке ОС. Отдельный непривилегированный UID Caddy; без возможности менять сеть/firewall.

Выход: INPUT default drop; SSH TCP 22 от 193.233.22.225, WG UDP 51820 от 193.233.22.225, established/related, loopback и нужный ICMP; DHCP сохранить, если требуется образом ОС. Сначала добавить разрешение SSH и проверить вторую сессию, потом закрывать остальное. INPUT со стороны wg0 к хосту закрыт. FORWARD разрешает только 10.77.0.2 → внешний интерфейс и обратные established/related; блокирует локальные/служебные назначения. SNAT/MASQUERADE только для 10.77.0.2/32. Включить только IPv4 forwarding. Не устанавливать 3x-ui/Xray.

## 4. Порядок исполнения после согласования

1. Закрыть условия раздела 1, выбрать доступный поддерживаемый LTS-образ (кандидат Ubuntu 24.04 LTS), зафиксировать адреса, интерфейсы и версии пакетов. Проверить резервные копии/консоли и механизм отката.
2. Переустановить только HostHatch через панель с публичным ключом. Через консоль сверить fingerprint; восстановить hosth-exit через kvmka-entry. Проверить новую SSH-сессию до любых ограничений firewall. Проверить DNS/HTTPS/IP повторно.
3. Установить минимальные пакеты WireGuard/nftables; создать ключи на узлах с правами 0600 вне репозитория. Настроить выход, затем namespace/WG входа. Проверить handshake, счётчики в обе стороны, MTU, DNS и HTTPS из namespace. Не считать TCP-доступность проверкой UDP.
4. Применять firewall атомарно после проверки синтаксиса. Перед каждой сетевой правкой сохранить состояние и поставить таймер отката, независимый от SSH. Держать две SSH-сессии и консоль. Отменять откат только после НОВОГО подключения с Windows к обеим VDS; существующая сессия недостаточна.
5. Настроить зависимости systemd: namespace/firewall → WireGuard → Caddy/релей. Запуск при ошибке защитных правил запрещён. Установить фиксированную проверенную версию Caddy с naive-веткой forwardproxy, отдельные учётные данные пользователей, домен и доверенный TLS; начать с HTTP/2 TCP 443. TCP 80 — только HTTP redirect/ACME. UDP 443 не открывать без необходимости. Произвольный UDP и UDP-over-TCP требуют отдельной проверки серверной поддержки.
6. Проверить отдельные профили SFA/Hiddify и выполнить приёмку. Затем можно подключать всю группу без миграции старого HostHatch. Подготовить инструкции по отзыву доступа, обновлению и восстановлению.

## 5. Приёмка

- Новый SSH входа и SSH выхода через ProxyJump работает до/после firewall, остановки WG и перезагрузки.
- Сайты видят 85.155.184.194; DNS прокси проходит через WG. На ens3 входа нет прямых соединений Caddy к сайтам/DNS (контроль пакетами и счётчиками).
- При остановке WG, удалении маршрута, недоступности выхода, перезапуске служб и загрузке ОС пользовательский трафик блокируется без fallback. Проверить новые и существующие соединения, DNS, IPv6. Все эти воздействия проводить только после согласования.
- Проверить сертификат, продление ACME, отсутствие открытого неавторизованного прокси, ограничения доступа к внутренним адресам, индивидуальный отзыв пользователя.
- Российские банки/Android Auto остаются напрямую; зарубежные ресурсы и загрузки ChatGPT работают через выход. Проверить DNS split, Per-App и TCP fallback; клиентские профили старой схемы сохранить.
- Проверить большие загрузки, MTU, задержку, 12 одновременных пользователей; целевые показатели скорости согласовать после базовых замеров. Один успешный запрос не доказывает длительную устойчивость.
